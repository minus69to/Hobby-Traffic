# DECISIONS

Ambiguities resolved autonomously, with the reason. Newest at the bottom.

1. **Branch.** The spec says push to `main`; the session's instructions name the feature branch `claude/great-goodall-2fl9mt`. All work is pushed to that branch (the owner can fast-forward `main`). Reason: the branch instruction is the more specific one.
2. **Docker.** No Docker daemon is available in this VM. `Dockerfile` and `docker-compose.yml` are written and linted by eye but not executed; mosquitto runs as a local apt-installed process for tests. Stated in README.
3. **Traffic-light control path.** Instead of relying on SUMO's built-in programs, every controller (fixed-time, max-pressure, PPO, the MQTT service) produces a *phase request*, the safety shield FSM turns it into a red/yellow/green state string, and that string is written to SUMO every step with `setRedYellowGreenState`. Reason: one code path, one shield, exact parity between training, evaluation and deployment.
4. **Gridlock prevention.** With the sublane model *and* interacting pedestrians, a controller that starves a movement can deadlock the junction box (vehicles inside the junction wait for pedestrians who are jammed on an overcrowded corner, and vice versa); without either feature no deadlock occurs. Fix: `--ignore-junction-blocker 30` and `--pedestrian.striping.jamtime 60` (both in `configs/sim.yaml`). Teleporting stays disabled (`--time-to-teleport -1`) so no vehicle is ever removed from a jam and throughput numbers are honest. Verified on the worst case (max-pressure, morning peak): zero teleports, throughput restored.
5. **Max-pressure baseline.** The spec allows "SUMO actuated or max-pressure"; max-pressure is used because it runs through the same shield/mask path as PPO (SUMO's built-in actuated program would bypass the shield).
6. **Pedestrian wait** is taken from SUMO's `personinfo` `waitingTime` (time standing still during the walk, which at this geometry is time waiting at a crossing). Pedestrian *counts* per corner walking area are what the agent observes (the HUD calls them "pedestrians waiting per crossing").
7. **Reward design.** `r = -1.0 * ΔW/100 - 0.2 * max(P,0)/100 - 0.3 * N_ped/10 - 0.05 * switch`, with `W` the sum of accumulated waiting time of vehicles on the incoming lanes (SUMO `--waiting-time-memory 1000`), `P` the junction pressure, `N_ped` waiting pedestrians and `switch` an indicator of a phase change. The waiting-time *difference* is the dense signal used by sumo-rl; it telescopes over an episode, so the pressure term adds an absolute level penalty, the pedestrian term makes the walk phases matter (pedestrians are not in `W`), and the switch penalty discourages min-green flickering (each switch costs 5 s of all-red/yellow). Scales were chosen so that each term is O(1) per step in the morning peak.
8. **Max-pressure baseline keeps its textbook form.** The arg-max of phase pressure (halting vehicles in minus halting vehicles out) with the same min/max-green mask. In this lefthand layout the protected right turn shares lane 3 with the through movement, so the through phases always carry more pressure and the right-turn phase is only reached when the shield forces a rotation after max-green; the shared lane then sits with a blocked head vehicle. That costs capacity at low demand (off-peak waiting time roughly 2-3x fixed-time) while the same rule is far better than fixed-time at the peak. Variants with cyclic order, blocked-lane detection, count-based pressure or longer holds were tried and none dominated, so the canonical algorithm is reported as is and the weakness is discussed in the report rather than hidden by tuning.
9. **Replays use a 0.5 s simulation step** so positions can be sampled every 0.5 s (the spec); evaluation uses 1 s steps. The HUD numbers therefore come from the replay run itself (its manifest), not from the evaluation tables.
10. **Citations.** Only GitHub was reachable from the VM, so references were verified through the official repositories' README citation blocks; unverifiable papers are listed in `docs/CITATIONS_VERIFIED.md` and not cited.
11. **Adversarial review (M3/M4 time, 124 subagent runs).** 39 findings, 31 confirmed by at least two of three refuters and fixed in one pass; the 8 refuted ones are listed in `REVIEW.md`. Two confirmed findings affect runs that were already in progress and could not be restarted within the budget: (a) time-limit episode ends were not flagged as truncated, so PPO did not bootstrap the terminal value on the last transition of each episode (seeds 13, 42, 2026 and the BC run trained this way; the fix is in `vec_env.py` for every later run and the grid runs); (b) the reward in the `noisy` scenario was computed from the noisy sensor copy (that scenario is not in the training curriculum, so training is unaffected; evaluation rewards are not reported). Metrics changed before the final evaluation: travel/waiting means use completed trips only, undeparted vehicles and insertion delay are counted (`mean_depart_delay`, `unfinished_share`), throughput is per hour, and the pooled PPO row uses a seed-level cluster bootstrap. Replays are regenerated after the fixes (frame f now holds positions at f*dt).
12. **Fallbacks after the VM restart (03:34 UTC on the deadline day).** Seed 2026 never trained (crash described in PROGRESS.md) and the machine restarted before it could be rerun; with four hours left the spec's fallback applies: two seeds on `single`, no grid run. The graph-coordination component (`drs/gnn.py`, `configs/train_grid_*.yaml`) is implemented and unit-tested but was not executed; its report section says so. The forecasting experiment and the third seed were run afterwards as follow-up work (branch `followup-runs`). The imitation comparison uses the BC+PPO run's evaluations up to 245k steps (the run was interrupted) against the same window of the from-scratch run.
